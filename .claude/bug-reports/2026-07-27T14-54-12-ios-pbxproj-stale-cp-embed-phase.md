## Reproduction

1. `cd mobile && export PATH="$HOME/development/flutter/bin:$PATH"`
2. `git diff ios/Podfile.lock ios/Runner.xcodeproj/project.pbxproj` (working tree as committed by the dev for this slice) — Podfile.lock is Flutter-pod-only, as claimed.
3. Run `flutter build ios --config-only` (this re-runs `pod install` as part of Flutter's iOS build prep).
4. `git diff ios/Podfile.lock ios/Runner.xcodeproj/project.pbxproj` again — both files change *again*, on top of the dev's already-committed diff.

## Expected

The Podfile.lock/pbxproj checked in for this slice should already reflect a fully-converged `pod install` output (i.e. running `pod install` / `flutter build ios --config-only` again should be a no-op diff), since the PR claims "pbxproj regenerated by pod install."

## Actual

A second `pod install` pass (triggered transitively by `flutter build ios --config-only`) further removes a leftover `43C8BDAA8314AA5752E7B5D0 /* [CP] Embed Pods Frameworks */` `PBXShellScriptBuildPhase` (and its reference in the Runner target's build-phase list) that the dev's committed pbxproj still contained, even though there are now zero CocoaPods pods (`Podfile.lock` lists only `Flutter`). The referenced xcfilelists under `Pods/Target Support Files/Pods-Runner/` do still exist after a fresh `pod install` (CocoaPods emits empty lists), so this phase is currently a harmless no-op rather than a hard build failure — but it's dead config that a single regeneration pass didn't fully prune.

## Notes

Bundle identifier, `CODE_SIGN_ENTITLEMENTS`, `IPHONEOS_DEPLOYMENT_TARGET = 15.5`, and the `GoogleService-Info.plist` Resources entry all remained correct both before and after this second regeneration pass — this is purely a stale build-phase-pruning issue, not a data-loss risk. Fix is mechanical: run `flutter build ios --config-only` (or `pod install` from `ios/`) one more time locally and commit the resulting `Podfile.lock` + `project.pbxproj` diff. Did not attempt an actual device/simulator build (iOS simulator toolchain is broken in this sandbox per dispatch instructions) — only `--config-only`, which succeeded (exit 0).

## Fix

The converged pbxproj/Podfile.lock state (produced by the second `pod install` during the test pass) is committed together with the stage-2 slice — the stale `[CP] Embed Pods Frameworks` phase is gone. No code change was needed.
